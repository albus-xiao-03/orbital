## 1. Summary

`orbital` will be a Python package that uses only the standard library. Its subpackage `orbital.bridges` lets a ChatGPT agent in one Docker Sandbox hand a prompt to Claude Code in a second Docker Sandbox and get Claude's answer back. The two sides talk only over the network.

- **Claude side.** `orbital-bridge serve` runs a small HTTP server. It authenticates every request, passes the prompt to `claude -p`, and keeps the result under the task id. Claude does the work; the bridge only carries the prompt and the result.
- **ChatGPT side.** `orbital-bridge submit …` (or the `BridgeClient` Python API) creates the task id, sends the prompt, polls, and prints one structured JSON result.
- **Results.** Every result carries the task id and one status: `running`, `succeeded`, `failed`, `timed_out`, `communication_error` or `rejected`. It also carries either Claude's response or an error code with a message. §7 defines exactly what each status claims. In particular:
  - `succeeded` means the Claude Code process reported that it completed successfully. It does **not** mean anyone checked that the delegated objective was achieved.
  - `timed_out` means the Claude side confirmed that the execution reached its deadline and was terminated. A client that stops waiting reports `running` instead.
- **Trust.** Requests and responses are signed with HMAC-SHA256 under a pre-shared key. Only responses whose signature verifies are authoritative. Anything else is reported as `communication_error`.
- **Verification boundaries** (§3):
  - The ChatGPT side is simulated with `BridgeClient` and the CLI. No OpenAI account or credential is ever used.
  - Your Claude account is used only for bounded runs: Phase F, which confirms the real `claude -p` contract before any code is written, and Stage R, the local verification with real Claude.
  - You build and operate the two sandboxes for the final test. Setup commands (§14) and the test procedure (§16) are prepared for you.

### Interpretations (adopted; see decision Q2 in §17)

- **I1. Commit granularity.** I read `initial`, `change` and `remove` as file-level operations. Each commit therefore contains exactly one file and one operation on it:
  - creating it (subject prefix `add:`, which matches this repository's history);
  - modifying it (prefix `change:`);
  - deleting it (prefix `remove:`).

  Line-level edits are not split further. Code files and documentation files never share a commit. Every commit has a subject, a descriptive body and the `Co-Authored-By` trailer.

- **I2. "Static helper objects".**
  - An *implementation component* is a type, together with its methods: a class, dataclass, enum, `Protocol`, or a subpackage's exception family. An entry-point callable such as `main()` also counts.
  - A *static helper object* is anything that supports a component without being one: a module-level function, a module-level constant or table, or a `@staticmethod` used as a utility.
  - Logic used inside only one method stays inline in that method.
  - Anything factored out to be shared is a helper, and it moves to a `utils` module (rule M2 in §6).

- **I3. Temporary files.** These are the files I create to get the work done. Program-generated files (caches, `*.egg-info`, `build/`, Claude Code's own session transcripts, and files Claude Code creates in the `.tmp` working directories during runs) are outside the definition.

- **I4. Tests.** The temporary harness may be as thorough as needed. It is never committed and never deleted.

## 5. Architecture and key decisions

### Topology

```
ChatGPT sandbox
  ChatGPT agent, or you, running the orbital-bridge CLI
    └─ orbital-bridge submit …  ............................. BridgeClient
         │  HTTP/1.1 + JSON, HMAC-signed in both directions
         │  leaves through the sandbox egress proxy (which applies network policy)
         ▼
Docker host   http://host.docker.internal:8765  →  published port  →  Claude sandbox :8765
              (you set up port publishing and policy; orbital never touches Docker)
         │
         ▼
Claude sandbox
  orbital-bridge serve  ..................................... BridgeServer (binds 0.0.0.0:8765)
    ├─ authenticate each request, sign each response
    ├─ TaskSupervisor + TaskRegistry: at most one running task; results kept by task id
    └─ ClaudeCodeExecutor
         └─ claude -p --output-format json --session-id <task_id>   (prompt on stdin)
              Claude performs the task; the bridge only carries prompt and result
```

### Happy-path sequence

```
ChatGPT side     BridgeClient                          BridgeServer                Claude Code
     │ run(prompt)   │                                       │                          │
     │──────────────▶│ task_id = uuid4()                     │                          │
     │               │ POST /v1/tasks (signed) ─────────────▶│ authenticate, admit      │
     │               │◀────────── 202 running (signed) ──────│ start worker ───────────▶│ claude -p  (stdin)
     │               │ GET /v1/tasks/{id}, every 2 s ───────▶│                          │ …works…
     │               │◀────────── 200 running ───────────────│                          │
     │               │                                       │◀──── JSON result ────────│ exits
     │               │ GET /v1/tasks/{id} ──────────────────▶│ reaped → succeeded       │
     │               │◀────── 200 succeeded + response ──────│                          │
     │◀─ TaskResult ─│ verify signature and task_id          │                          │
```

### Decisions

| # | Decision | Rationale | Rejected alternatives |
|---|---|---|---|
| D1 | **Roles.** The Claude side is the HTTP server and the ChatGPT side is the client. One port is published from the Claude sandbox. | This matches the direction of delegation and needs only one inbound port. Outbound HTTP through the proxy is the supported way out of a sandbox. | A ChatGPT-side server polled by Claude: it just moves the port. A third relay process: an extra component, outside the scope. |
| D2 | **Transport.** HTTP/1.1 and JSON on the standard library. | The sandbox egress is an HTTP forward proxy. Nothing has to be installed in either sandbox. | Raw TCP framing: may not pass the proxy. WebSockets or gRPC: need dependencies and are uncertain through the proxy. |
| D3 | **Asynchronous tasks.** `POST` returns `202` straight away and the client polls with `GET`. | Claude tasks can run for minutes or hours. A dropped connection loses nothing while the server keeps running. | One long blocking request: dies at proxy idle timeouts. |
| D4 | **Task identity.** The client generates a UUID4 before any I/O. Within one server lifetime, the server refuses an id reused with different content and treats an identical resubmission as idempotent. | Every outcome carries the id, including a submission that failed (O8), and retries are safe. These guarantees do **not** survive a server restart (§10). | Server-assigned ids: a failed submission would have no id. |
| D5 | **Capacity.** At most one task runs at a time; any other submission gets `rejected` / `server_busy`. | Concurrency and workload management are out of scope. | A FIFO queue: that is workload management. |
| D6 | **Authentication.** HMAC-SHA256 with a pre-shared 256-bit key. Requests are signed with a timestamp and nonce and checked against a replay cache. The server signs every response to a request with a well-formed nonce, including authentication failures. The client treats only verified responses as authoritative (§9). | Works over plain HTTP through the proxy. The key is never transmitted. A proxy page or impostor can never produce an authoritative result. | A bearer token: replayable, and responses are not authenticated. mTLS: certificate handling, and a risk of proxy interception. |
| D7 | **Delegation.** Run `claude -p --output-format json` with the prompt on stdin, in its own process group, with the deadline enforced. The details are confirmed in Phase F before implementation. | Claude does the work (O12). Stdin avoids the Linux limit of 128 KiB per argument. The JSON output carries explicit error flags. | The Agent SDK: a third-party dependency. `--output-format text`: gives no error signal. |
| D8 | **Reporting.** The client API returns a `TaskResult` for every outcome and raises exceptions only for programmer errors. | Nothing is silently discarded (AC4). | Exceptions for network errors: too easy to lose. |
| D9 | **Status claims.** Each status makes one precise claim about the Claude Code process (§7). Only the server can report that a task ended. | A failure can never be read as success, and a gap in communication can never be read as an outcome. | — |
| D10 | **Two time limits.** The *execution timeout* is sent with the task and is enforced and confirmed only by the server. The *wait budget* is how long this client call waits; it is never sent. Running out of wait budget never reports `timed_out`. | A client that stops waiting knows nothing about whether the task has ended. | A single client-side timeout reported as `timed_out`. |
| D11 | **State.** An in-memory registry, keeping the last 100 finished results. | R1 is about communication. The limits this creates across restarts are stated explicitly (§10). | A persistent store: outside the R1 scope (§18). |
| D12 | **Footprint.** Standard library only, Python 3.11 or later. | Portable to the other sandbox. | requests, aiohttp or FastAPI. |
| D13 | **ChatGPT interface.** A CLI with four commands (`serve`, `submit`, `wait`, `ping`), plus the Python API. | A sandboxed ChatGPT agent or a person can run the same shell commands, and JSON output is unambiguous. Development and tests need no OpenAI agent. | An MCP tool server: deferred (§18). |

### Simplification review (80 → 49 files, revision 2)

| Removed or merged in revision 1 | Replaced by | Why it was unnecessary |
|---|---|---|
| The `protocol/` subpackage: `Route`, `RouteMatch`, `Header`, `MessageCodec`, `ProtocolError` and two utils modules (9 files) | `to_dict`/`from_dict` methods on the model types; API paths and strict JSON helpers in `bridges/utils.py`; header names in `auth/utils.py`; `ValueError` | Three endpoints and four small message shapes (request, record, error, health) do not need routing or codec types. |

| `TaskService`, `TaskRecord`, `TaskRunner`, `BridgeHTTPServer`, and three server utils modules | `TaskSupervisor` (admits and runs tasks); `TaskRegistry` stores results directly; `BridgeServer` *is* the `ThreadingHTTPServer` subclass; one `server/utils.py` | Facade and wrapper layers with no logic of their own. |
| `MessageSigner` + `MessageVerifier`, `RequestCredentials` | One `MessageAuthenticator`, which reads and writes its own headers | Two halves of one scheme that share the key and the canonical strings. |
| `RetryPolicy`, `TransportReply`, `TransportFailure` | Backoff written inline in `BridgeClient`; the transport returns `(status, body)` for a verified reply, or an `ErrorDetail` | A five-step backoff and a two-way result do not need their own types. |

| The `--detach` and `--task-id` options | `--max-wait 0`; task ids are always generated by the client | The same capability, with fewer ways to misuse it. |

These were kept deliberately:

- **`ProcessRunner` and `ProcessOutput` stay separate from `ClaudeCodeExecutor`.** OS-level supervision is the hardest code in the package and must be testable with ordinary commands.
- **`HttpTransport` stays separate from `BridgeClient`.** One handles signing, verification and classification; the other handles task semantics.
- **`TaskRegistry` stays separate from `TaskSupervisor`.** One holds the admission and retention rules; the other manages the thread and the process.
- **`NonceCache` stays separate.** It is server-only replay state with its own expiry and capacity rules.
- **Each model type and each CLI command keeps its own file,** as the decomposition rule requires.

### Module rules

- **M1 — One component per file.** Each implementation file holds one public component and its methods. The only exception is `errors.py`, which holds the exception family of its subpackage.
- **M2 — Helper placement (interpretation I2).** Helpers live in `<subpackage>/utils.py` when they form one cohesive group. They live in a `<subpackage>/utils/` subpackage, with one module per owning implementation file, when they belong to different implementation files. The resulting placement:

  | Location | Helpers |
  |---|---|
  | `bridges/utils.py` | shared by several subpackages |
  | `models/utils.py`, `auth/utils.py`, `server/utils.py`, `cli/utils.py` | one cohesive group each |
  | `executor/utils/` and `client/utils/` | helpers of two different implementation files each |

- **M3 — No import cycles.**
  - Subpackage `__init__.py` files contain only a docstring.
  - The public API is re-exported only from `orbital/bridges/__init__.py`.
  - Internal imports always name leaf modules.
  - The handler refers to `BridgeServer` through a `TYPE_CHECKING`-only import.
- **M4 — Layering.** `models`, `auth` and `bridges/utils.py` depend on nothing else in `orbital`. The other subpackages depend on each other as follows:

  | Subpackage | Depends on |
  |---|---|
  | `executor` | `models` |
  | `server` | `models`, `auth`, `executor`, `bridges/utils.py` |
  | `client` | `models`, `auth`, `bridges/utils.py` |
  | `cli` | all of the above |

  `server` and `client` never import each other.
- **M5 — Style.** Full type hints, clean under `mypy --strict` (target Python 3.11) and `ruff check` / `ruff format`. Public components get docstrings. Any `noqa` must state its reason; for example, binding `0.0.0.0` is intentional (S104) and the single Claude subprocess call is intentional (S603).

## 7. Domain model and status semantics

### What each status claims

| Status | Task outcome settled? | Exact claim | Who can produce it |
|---|---|---|---|
| `running` | no | At the server's last report, the Claude Code process was executing. It may have finished since. | server snapshot |
| `succeeded` | yes — ended | The Claude Code process exited with code 0 **and** reported a successful result. `response` is its final result text, passed through unchanged. | server only, after the process is reaped |
| `failed` | yes — ended or never started | The process ended without reporting success, could not be started, or the bridge failed while running it. In every case the process is no longer running. Partial work may exist. | server only, after the process is reaped |
| `timed_out` | yes — terminated | The process was still running at its execution deadline. The server terminated it **and confirmed that it exited**. | server only |
| `rejected` | yes — not executed | The request was refused before execution. Either a verified server response says so, or the client's local pre-check stopped it from being sent. | server (verified) or the client's pre-check |
| `communication_error` | **unknown** | No authoritative answer was obtained. The task may never have started, may be running, or may have finished. | client only |

#### `succeeded` is not verification of the objective

`succeeded` reports what the Claude Code process said about its own run. The bridge does not evaluate the response, does not inspect the Claude side's workspace, and does not check that the delegated objective was achieved. Doing any of that would mean performing or judging the task, which objective 12 rules out. In practice:

- A `succeeded` response can still say the work was partial, or that Claude could not do what was asked. Phase F saw exactly this: in F-5 a file write was denied by permissions, yet Claude Code reported `subtype: "success"`, `is_error: false` and `terminal_reason: "completed"`, with a response explaining that it could not do the task.
- If Claude Code itself reports success too early, the bridge passes that on as it is (R3).

Judging the response is the ChatGPT side's job. The CLI documentation and the agent snippet (§12) say this explicitly.

#### Execution deadline versus waiting budget

- **Execution timeout** (`execution_timeout_seconds`) is sent with the task.
  - Only the server enforces it, and only the server reports `timed_out`.
  - It does so only after the Claude Code process has exited following termination (§10).
  - Until then, the task is reported as `running`.
- **Wait budget** (`max_wait_seconds`) is local to one client call and never sent.
  - When it runs out, the client returns the last snapshot it received from the server: status `running`, error code `wait_deadline_reached`.
  - The message says the task has **not** been confirmed finished, and how to retrieve it later.
  - If the most recent exchange had failed when the budget ran out, the result is that `communication_error` instead (§11).
  - A deliberate zero-wait poll (`max_wait_seconds = 0`) returns the snapshot without that code.
- **Stopping waiting never cancels the task.**
- **Defaults.** The default wait budget is the execution timeout plus 60 s. That way the server's confirmed `timed_out` normally arrives before the client gives up.

### `ErrorCode`

Each code belongs to exactly one category, given by `ErrorCode.category`. A `TaskResult` whose error code does not match its status is invalid.

| Code | Category | Produced by | Meaning |
|---|---|---|---|
| `unauthorized` | `rejected` | server: **verified** 401 | Authentication failed; the reason in the message is trustworthy |
| `invalid_request` | `rejected` | server: verified 400/404/405/411 | The request was malformed, invalid, or for an unknown route |
| `payload_too_large` | `rejected` | server: verified 413, or the client's pre-check | The request body is over the size limit |
| `server_busy` | `rejected` | server: verified 409 | Another task is running; the message names it |
| `task_id_conflict` | `rejected` | server: verified 409 | This server instance has already used the task id |
| `connection_failed` | `communication_error` | client | Could not connect (refused, DNS failure, unreachable) |
| `connection_interrupted` | `communication_error` | client | The connection dropped mid-exchange |
| `request_timeout` | `communication_error` | client | No HTTP response within the per-request timeout |
| `gateway_error` | `communication_error` | client: unverified 502/503/504 | An intermediary reported a gateway failure |
| `network_policy_blocked` | `communication_error` | client: unverified 403 | The sandbox proxy appears to have refused the request; its message is quoted as unverified |
| `unverified_auth_rejection` | `communication_error` | client: unverified 401 | A rejection that cannot be verified. The usual cause is a different key on each side (§9). |
| `response_unverified` | `communication_error` | client | Any other response without a valid signature |
| `invalid_response` | `communication_error` | client | A verified response that is malformed or inconsistent |
| `unknown_task` | `communication_error` | server: verified 404 | This server instance has no record of the task (§10) |
| `server_error` | `communication_error` | server: verified 500 | An unexpected bridge-server error |
| `claude_error` | `failed` | executor | Claude Code reported an error result |
| `executor_failed` | `failed` | executor | Claude Code exited abnormally without a valid success result |
| `executor_unavailable` | `failed` | executor | Claude Code could not be started |
| `invalid_executor_output` | `failed` | executor | Claude Code's output could not be interpreted |
| `execution_cancelled` | `failed` | executor | Execution was stopped because the server shut down |
| `internal_error` | `failed` | server supervisor | An unexpected bridge error; the process was terminated and reaped first |
| `execution_timeout` | `timed_out` | executor | The deadline was reached; the process was terminated and has exited |
| `wait_deadline_reached` | `running` | client | The client stopped waiting; the task was not confirmed finished |

### Types and invariants

`ErrorDetail`, `TaskRequest` and `TaskResult` are frozen dataclasses. Each is validated in `__post_init__` and invalid values raise `ValueError`. Each has strict `to_dict()` / `from_dict()` methods, which form the wire format (§8).

- **`ErrorDetail(code: ErrorCode, message: str)`.** The message is non-empty and capped at 4,000 characters; longer messages are truncated with a marker.
- **`TaskRequest(task_id, prompt, execution_timeout_seconds)`.**
  - `task_id` is a canonical, lowercase UUID version 4.
  - `prompt` is a `str` that is not blank.
  - `execution_timeout_seconds` is an `int` of at least 1; a `bool` is not accepted. The server also enforces its own maximum.
- **`TaskResult(task_id, status, response, error)`** has these invariants:
  - `running` → `response is None`, and either `error is None` or `error.code` is `wait_deadline_reached`.
  - `succeeded` → `response` is a `str` (it may be empty) and `error is None`.
  - Any other status → `response is None`, `error` is present, and `error.code.category` equals `status`.

```json
{"task_id": "0b6c1c2e-6f5d-4c9a-9a51-3f2f6d0c8e11", "status": "succeeded", "response": "…Claude's final message…", "error": null}
{"task_id": "0b6c1c2e-6f5d-4c9a-9a51-3f2f6d0c8e11", "status": "running", "response": null,
 "error": {"code": "wait_deadline_reached", "message": "Stopped waiting after 1860 s; the task was still running at 2026-11-12T10:31:02Z and has not been confirmed finished. Retrieve it with: orbital-bridge wait 0b6c…8e11"}}
```

## 8. Wire protocol v1

### Endpoints

| Method and path | Purpose | Success | Errors |
|---|---|---|---|
| `POST /v1/tasks` | Submit a task | `202` for a new task; `200` for an identical resubmission within this server's lifetime | 400, 401, 409, 411, 413 |
| `GET /v1/tasks/{task_id}` | Current record of a task | `200` | 401, 404 |
| `GET /v1/health` | Authenticated round-trip check | `200` | 401 |

### Bodies

All bodies are UTF-8, compact JSON objects.

- **Submit request.** Exactly these keys: `{"task_id": "<uuid4>", "prompt": "<text>", "execution_timeout_seconds": 1800}`.
- **Task record** (`200`/`202`). `TaskResult.to_dict()`. The server only ever reports `running`, `succeeded`, `failed` or `timed_out`.
- **Error.** `{"error": {"code": "<ErrorCode>", "message": "<text>"}, "task_id": "<uuid>" or null}`.
- **Health.** `{"service": "orbital-bridge", "protocol_version": "1"}`.

Decoding is strict on both sides. A message is rejected if it:

- is not a JSON object at the top level;
- has duplicate keys, `NaN` or `Infinity`;
- has unknown or missing keys;
- has a value of the wrong type (`true` is not an integer).

### Headers

| Header | Direction | Value |
|---|---|---|
| `X-Orbital-Protocol` | both | `1` |
| `X-Orbital-Timestamp` | request | Unix time in whole seconds |
| `X-Orbital-Nonce` | request | 16 random bytes as 32 lowercase hex characters |
| `X-Orbital-Signature` | request and response | HMAC-SHA256 as 64 lowercase hex characters |
| `Content-Type` / `Content-Length` | both | `application/json; charset=utf-8` and the exact byte length. Chunked bodies are not supported. |
| `WWW-Authenticate` | `401` response | `ORBITAL-HMAC-SHA256` |

Every response also carries `Connection: close` and `Cache-Control: no-store`.

### Signatures

The canonical strings are joined with `\n`, with no trailing newline. The signature is `hex(HMAC-SHA256(key, utf8(canonical)))`.

```
request:                  response:
ORBITAL-HMAC-SHA256       ORBITAL-HMAC-SHA256
1                         1
request                   response
<METHOD>                  <METHOD of the request>
<TARGET>                  <TARGET of the request>
<TIMESTAMP>               <NONCE of the request>
<NONCE>                   <HTTP status code>
<SHA256-hex of body>      <SHA256-hex of body>
```

- The `request` and `response` labels separate the two kinds of signature, so neither can be replayed as the other.
- `TARGET` is the origin-form path. The server normalises absolute-form targets sent through a proxy. The client signs only the path of the URL.

### Statuses and the signing rule

**The server signs every response whose request carries a well-formed `X-Orbital-Nonce`.** That includes `401`, `411` and `413`. Two kinds of response are unsigned: responses to requests without a well-formed nonce, and errors raised by the HTTP library before the handler runs. A signature proves the response came from the server only to a client that holds the same key (§9).

| Status | When |
|---|---|
| `200` | A task record (`GET`, idempotent `POST`) or the health check |
| `202` | A new task was accepted |
| `400` | Invalid JSON, fields or values (`invalid_request`) |
| `401` | Authentication failed (`unauthorized` plus a reason) |
| `404` | Unknown task (`unknown_task`) or unknown route (`invalid_request`) |
| `405` | Method not allowed (`invalid_request`) |
| `409` | `server_busy` or `task_id_conflict` |
| `411` | Missing `Content-Length` on `POST`, a chunked body, or a body on `GET` (`invalid_request`) |
| `413` | `Content-Length` over the limit (`payload_too_large`); the body is not read |
| `500` | Unexpected server error (`server_error`) |

The limits are a request body of at most 1 MiB, `execution_timeout_seconds` between 1 and 14,400, and a socket read timeout of 30 s per connection.

## 9. Authentication and security model

### Key

- Generate a key with `python3 -c "import secrets; print(secrets.token_urlsafe(32))"`, which gives 32 random bytes as 43 base64url characters.
- `SharedKey` accepts only text that decodes to at least 32 bytes.
- The key reaches each sandbox only through its own environment variable `ORBITAL_BRIDGE_KEY`. There is no CLI flag for it and no shared key file.
- `repr()` of a `SharedKey` is redacted, and the key is never logged.

### Server-side request verification

The server runs these checks in order and returns `401` with a coarse reason on the first failure. The reason is never secret.

1. All credential headers are present and well-formed. Reasons: `missing_credentials`, `malformed_credentials`.
2. `X-Orbital-Protocol` is `1`. Reason: `unsupported_protocol`.
3. The timestamp is within ±300 s of the server clock. Reason: `timestamp_out_of_window`.
4. The signature matches, compared in constant time with `hmac.compare_digest`. Reason: `invalid_signature`.
5. The nonce has not been seen within the last 600 s. Nonces are recorded only after the signature has verified. Reason: `replayed_nonce`.
6. The cache is bounded at 100,000 entries. If it is still full after expired entries are purged, the request is refused rather than weakening replay protection. Reason: `nonce_cache_full`.

Authentication happens before routing and before any JSON parsing. An unauthenticated request never reaches the supervisor or the executor.

### How the client treats responses

**Only a verified response is authoritative.** A response counts as verified when its `X-Orbital-Signature` checks out under the client's own key against:

- the request's method, target and nonce;
- the response's status code;
- the response body.

| Response | How it is reported | What is trusted |
|---|---|---|
| Verified `2xx` record | The record's status | Everything in it |
| Verified error, including a **verified 401** | `rejected` / `unauthorized`, or the category of the body's code | The error code and the reason. A verified 401 happens when both sides hold the same key but a check failed, for example clock skew or a replay. |
| **Unverified 401** (no signature, or one that does not check out under the client's key) | `communication_error` / `unverified_auth_rejection` | **Nothing.** The message quotes up to 500 characters of the body, labelled as unverified, and gives the likely causes: the two sides hold different `ORBITAL_BRIDGE_KEY` values, or an intermediary answered. It states that the task's state is not confirmed, although it was most likely not accepted. |
| Unverified 403 / 502 / 503 / 504 | `communication_error` / `network_policy_blocked` or `gateway_error` | Nothing; the proxy's text is quoted as unverified, as a hint for the operator |
| Any other unverified response, including a `2xx` | `communication_error` / `response_unverified` | Nothing |

Two consequences follow:

- `succeeded`, `failed`, `timed_out` and server-side `rejected` can come **only** from verified responses. The only exception is `rejected` / `payload_too_large` from the client's own pre-check, where the request was never sent.
- A code claimed in an unverified body is never copied into the result's code.

**Why a wrong key appears as unverified.** When the client's key is wrong, the server's 401 is signed with the server's key, and the client cannot verify it. The bridge cannot tell that case apart from an injected 401, so it does not pretend to. `ping` shows the same `unverified_auth_rejection`, which makes a key mismatch quick to diagnose.

**Signing unauthenticated failures is safe.** It gives an attacker signed `401`/`411`/`413` responses only for nonces of their own choosing. A legitimate client's nonces are 128-bit random values, so these signatures cannot be substituted into its exchanges. The `request`/`response` labels stop them from being used as request signatures.

### Hygiene

- All `ORBITAL_BRIDGE_*` variables are removed from the Claude Code child environment.
- Logs never contain prompts, responses or the key.
- The server advertises a generic `Server` banner.
- There is no switch that disables authentication, and the server refuses to start without a valid key.

### Threat model and limitations

**Protected against:**

- Task submission or result reading by anyone who can reach the port without the key.
- Tampering with a request or response.
- Replaying captured requests.
- Any forged, injected or proxy-generated response being taken as authoritative.

**Not protected against:**

- **Confidentiality.** Plain HTTP means content can be read on the host's network path. TLS is deferred.
- **The key holder.** Anyone with the key has full delegation power.
- **Floods of unauthenticated requests.** Socket timeouts limit them, but they are not fully mitigated.

The Claude side runs each prompt with whatever permissions its Claude Code is configured to have. The sandbox is the isolation boundary.

## 10. Claude-side server and executor

### Request pipeline (`BridgeRequestHandler`)

1. **Normalise the target.** An absolute-form target from a proxy becomes origin-form.
2. **Check framing.** A `GET` must have no body. A `POST` needs `Content-Length` (otherwise `411`) and must be within the limit (otherwise `413`, without reading the body).
3. **Read** exactly `Content-Length` bytes, with a socket timeout of 30 s.
4. **Authenticate** (§9). On failure, return `401`.
5. **Route.** An unknown path gets `404` and a wrong method gets `405`.
6. **Decode strictly.** On failure, return `400`.
7. **Call `TaskSupervisor`.** It returns `202`, `200`, `404` or `409`.
8. **Respond,** signed whenever the request nonce was well-formed (§8), with `Connection: close`.

An unexpected exception in steps 5–8 returns `500 server_error` and is logged with a stack trace.

### Components

- **`TaskRegistry`** is a thread-safe, in-memory store for the current server process. `admit(request)` applies these rules in order:
  1. If the id is known and its result is retained with the same fingerprint (SHA-256 over the prompt and the timeout), return the existing result (`200`).
  2. If the id is known but the content differs, or its result has been evicted, raise `TaskConflictError` (`409`).
  3. If another task is running, raise `ServerBusyError` (`409`, naming the running id).
  4. Otherwise record a new `running` result (`202`).

  The registry keeps the 100 most recent finished results; it never evicts the running one. It remembers every id it has seen until the process exits.
- **`TaskSupervisor`** provides `submit(request)` (admit, then start one worker thread), `status(task_id)` and `shutdown()`.
  - The worker calls `ClaudeCodeExecutor.execute(request)` and records the `TaskResult` that comes back.
  - If anything raises, the supervisor first makes the executor terminate and reap the process, and only then records `failed` / `internal_error`.
  - A terminal status is never recorded while the Claude Code process may still be running.
- **`BridgeServer`** is a subclass of `ThreadingHTTPServer` with daemon threads, built from a `ServerConfig`. It wires together the `MessageAuthenticator` (with its `NonceCache`), the registry, the supervisor and the executor, and records its own start time for diagnostics.
  - It binds on construction, so `server_address` is known even when the port is 0.
  - `shutdown()` stops accepting connections, cancels the running task and waits for the process to be reaped (up to 10 s), then closes the socket.

### Executor (`ClaudeCodeExecutor` on top of `ProcessRunner`)

The contract below was confirmed against Claude Code 2.1.322 in Phase F (§15).

- **Command:**
  ```
  [claude_bin, *claude_args, "-p", "--output-format", "json", "--session-id", task_id]
  ```
  - The fixed flags come last.
  - `claude_args` defaults to `--permission-prompts none`, so a tool call that would prompt for permission is denied instead of blocking.
  - `ServerConfig` rejects `claude_args` that would change the output contract: `-p`/`--print`, `--output-format`, `--input-format`, `--session-id`, `-r`/`--resume`, `-c`/`--continue` and `--verbose`.
  - The session id is the task id. F-2 showed that Claude Code keeps sessions per working directory and refuses a reused id in the same directory (exit 1, `Session ID … is already in use`) before calling the API.
- **Input:** the prompt's UTF-8 bytes, written to stdin by a writer thread that then closes stdin.
- **Process setup:**
  - working directory `workdir`;
  - environment: the server's own, minus every `ORBITAL_BRIDGE_*` variable and minus the 13 session-scoped Claude Code variables observed in Phase F (`CLAUDECODE`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_EXECPATH`, `CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_CODE_MESSAGING_TOKEN`, `CLAUDE_CODE_SESSION_ATTENDED`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_EFFORT`, `CLAUDE_ENV_FILE`, `CLAUDE_MODEL`, `CLAUDE_PID`, `CLAUDE_REASONING_EFFORT`);
    - a server started from a plain shell has none of these. Removing them means a server started from inside a Claude Code session still runs every task as an independent session, in the configuration Phase F tested. The server also logs a warning at startup if `CLAUDECODE` is set;
    - every other variable passes through unchanged, including other `CLAUDE_*` configuration variables and `MCP_GATEWAY_URL`;
  - `start_new_session=True`, so the whole process group can be signalled.
- **Output capture:**
  - stdout is captured up to 32 MiB; beyond that it is flagged as truncated and drained;
  - stderr keeps its last 64 KiB.
- **Deadline or cancellation (descendant-tree termination, from F-4):**
  1. Snapshot the process's whole descendant tree from `/proc`. Claude Code runs its tool processes in **their own sessions**, outside its process group.
  2. Send `SIGTERM` to Claude's process group. In F-4, Claude terminated its own tool processes and exited with status **143** about 0.7 s later.
  3. After a 5 s grace period, send `SIGKILL` to the group **and** to every snapshotted or newly found descendant that is still alive. A group kill alone would miss tool processes if Claude were unresponsive.
  4. Wait for the Claude Code process to be **reaped**, and re-check that no snapshotted descendant is alive.

  Termination counts as confirmed only after step 4. Only then can `timed_out` or `execution_cancelled` be recorded; until then the task stays `running`. The result message notes any descendant whose termination could not be confirmed.

**Outcome mapping.** Success needs both exit code 0 and an explicit success report.

| Observation (after the process has been reaped) | Outcome |
|---|---|
| The executable is missing or not executable | `failed` / `executor_unavailable` |
| The deadline was reached and termination is confirmed | `timed_out` / `execution_timeout` |
| Cancelled by server shutdown and termination is confirmed | `failed` / `execution_cancelled` |
| Exit code 0, and the single stdout JSON object has `type: "result"`, `is_error: false`, `subtype: "success"`, a string `result`, and `terminal_reason: "completed"` whenever that field is present | `succeeded`, with `response` set to `result` verbatim |
| The result object has `is_error: true`, a non-success `subtype`, or a `terminal_reason` other than `completed` | `failed` / `claude_error`. The message includes `terminal_reason`, `api_error_status` (when not null), the subtype, and excerpts of `result` and/or `errors`. F-3 shows `subtype: "success"` together with `is_error: true` on an API error, so `subtype` is never enough on its own. |
| The result object says success but the exit code is not 0 | `failed` / `executor_failed`. The contradiction is reported; it is never treated as success. |
| No parsable result object, and the exit code is not 0 | `failed` / `executor_failed`, with the exit code or signal and the stderr tail. An example is a reused session id (`Session ID … is already in use`, F-2). |
| No parsable result object, and the exit code is 0; or stdout was truncated | `failed` / `invalid_executor_output` |

Only `result` is relayed. Every other field is ignored, including `usage`, `total_cost_usd`, `duration_*`, `num_turns`, `permission_denials` and `credential_expires_at`; F-1 returned 27 fields in all. Token and cost accounting is out of scope.

### Restart semantics

The registry exists only in the memory of one server process, so every restart, graceful or not, starts empty. **Idempotency, conflict detection, single execution and retention hold only within one server lifetime:**

| Guarantee | Within one server lifetime | After a restart |
|---|---|---|
| An identical resubmission (including the client's own automatic retry) returns the existing result without re-running | yes | **no.** The bridge accepts it as new. If the server uses the same workdir, Claude Code then refuses the reused session id (F-2), so the task does not run twice: the result is `failed` / `executor_failed`, with `Session ID … is already in use`. |
| An id reused with different content is refused (`task_id_conflict`) | yes | **no.** The bridge accepts it as new; with the same workdir, Claude Code refuses it as above. |
| A task id is executed at most once | yes | **Only while the workdir is unchanged and Claude Code still keeps that session's transcript.** Claude Code's per-directory session store refuses the reused id. With a different workdir, the task runs again. |
| Finished results can be retrieved (the last 100) | yes | **no.** `GET` returns a verified `404`, which the client reports as `communication_error` / `unknown_task`. |
| At most one task runs | yes | **only among tasks the new process knows about.** After a crash, an orphaned execution from the old process may still be running. |

How each way of stopping behaves:

- **Graceful stop** (`SIGINT`/`SIGTERM`): the running Claude Code process is terminated and reaped before the server exits, so nothing is left running. Its result is lost with the registry.
- **Crash or `SIGKILL` of the server:** the bridge gets no chance to terminate the Claude Code process. It can keep running as an orphan that the restarted server knows nothing about, and its result is lost. After a crash, look for leftover `claude` processes. Hardening this is deferred (§18).
- **Diagnosability:** the `unknown_task` message includes the server's start time and says whether this instance never saw the id or no longer retains its result. That lets an operator tell a restart apart from eviction.
- **Guidance for the ChatGPT side:** `unknown_task` means the outcome is unknown. Before re-running work that may have side effects, inspect the Claude side first. A new `submit` always uses a new task id.

### Shutdown and logging

- **Shutdown.** `SIGINT` and `SIGTERM` trigger the graceful stop described above.
- **Logging** goes to stderr:
  - `INFO`: startup (address, workdir, Claude binary and version; never the key), each task accepted, and each task finished (with task id, status, code, duration and the number of permission denials Claude Code reported);
  - `WARNING`: authentication failures;
  - `DEBUG`: polls.

## 11. ChatGPT-side client

### API

These methods never raise for task or communication outcomes. They raise `ValueError` or `TypeError` only for invalid arguments.

```python
client = BridgeClient(ClientConfig.from_env())
client.submit(prompt, *, execution_timeout_seconds=None) -> TaskResult        # running, or a failure
client.wait(task_id, *, max_wait_seconds=None) -> TaskResult                  # 0 = a single poll
client.run(prompt, *, execution_timeout_seconds=None,
           max_wait_seconds=None) -> TaskResult                               # submit, then wait
client.ping() -> ErrorDetail | None                                           # None = reachable and verified
```

### Algorithms

- **`submit`**
  1. Validate the arguments.
  2. Generate a UUID4 task id.
  3. Encode the body. If it is over `max_request_bytes`, return `rejected` / `payload_too_large` without sending anything.
  4. Send the `POST`. On retryable failures, retry it with the same body and a fresh nonce; this is idempotent within one server lifetime (§10).
  5. Map the reply (§9).
- **`wait`** polls every `poll_interval` (2 s) until the server reports a settled status. When `max_wait_seconds` runs out, it returns one of two results:
  - if the most recent exchange returned `running`: that snapshot with `wait_deadline_reached` (or the plain snapshot when `max_wait_seconds` was 0);
  - if the most recent exchange **failed**: that `communication_error`, whose message gives the time `running` was last confirmed.

  It never reports `timed_out` on its own.
- **`run`** calls `submit`, then `wait`. The default wait budget is the execution timeout plus 60 s.
- **Retries.**
  - The retryable codes are `connection_failed`, `connection_interrupted`, `request_timeout` and `gateway_error`.
  - Backoff is 1, 2, 4, 8, then 16 s, capped at 30 s.
  - At most 5 consecutive failures are allowed. The counter resets after any verified exchange, and retries never run past the wait budget.
  - If the retry budget runs out after the task was accepted, the result is `communication_error`, and the message says the task may still be running and can be retrieved with `orbital-bridge wait <task_id>`.

### Mapping replies to results

| Observation | Status | Code | Retried |
|---|---|---|---|
| Connection refused, DNS failure, unreachable | `communication_error` | `connection_failed` | yes |
| Connection reset, remote disconnected, incomplete read | `communication_error` | `connection_interrupted` | yes |
| Socket timeout | `communication_error` | `request_timeout` | yes |
| Unverified `502`, `503` or `504` | `communication_error` | `gateway_error` | yes |
| Unverified `403` | `communication_error` | `network_policy_blocked` | no |
| Unverified `401` | `communication_error` | `unverified_auth_rejection` | no |
| Any other unverified response, including a `2xx` | `communication_error` | `response_unverified` | no |
| Verified `200`/`202` with a valid record for this task id | the record's status | the record's code | — |
| Verified `2xx` that is malformed, has the wrong task id, or has a status the server never reports | `communication_error` | `invalid_response` | no |
| Verified `401` | `rejected` | `unauthorized` (with the trusted reason) | no |
| Verified `4xx`/`5xx` with a valid error body | the body code's category | `invalid_request`, `payload_too_large`, `server_busy`, `task_id_conflict`, `unknown_task` or `server_error` | no |
| Verified `4xx`/`5xx` with an unknown or inconsistent code | `communication_error` | `invalid_response` | no |
| The prompt is too large for the local limit (never sent) | `rejected` | `payload_too_large` | no |

### Proxy handling

- By default `urllib` honours `HTTP_PROXY` and `NO_PROXY`, which is required inside sandboxes. `--no-proxy` turns this off for direct loopback use.
- Text from the proxy is quoted, labelled as unverified, in the messages for `network_policy_blocked`, `gateway_error` and `unverified_auth_rejection`.
- `ClientConfig` accepts only `http://host[:port]` URLs, with no path, query or userinfo.

## 12. Command-line interface

The console script is `orbital-bridge`, which is the same as `python -m orbital.bridges`. Results are printed to stdout as a single JSON object; logs go to stderr.

| Command | Side | Purpose | Main options |
|---|---|---|---|
| `serve` | Claude | Run the bridge server. It first checks that the Claude binary and the workdir exist. | `--host`, `--port`, `--workdir`, `--claude-bin`, `--claude-arg` (repeatable), `--max-execution-timeout`, `--log-level` |
| `submit` | ChatGPT | Submit a prompt and wait for its result within the wait budget | the prompt as `PROMPT`, `--prompt-file PATH` or `-` (stdin); `--execution-timeout`; `--max-wait` (`0` returns straight after submitting); `--url`; `--no-proxy` |
| `wait` | ChatGPT | Retrieve a task, waiting up to `--max-wait` (`0` = a single poll) | `TASK_ID`, `--max-wait`, `--url`, `--no-proxy` |
| `ping` | ChatGPT | Authenticated round trip | `--url`, `--no-proxy` |

The exit code is determined only by the status that was printed:

| Exit code | Meaning |
|---|---|
| 0 | `succeeded`, as reported by Claude Code; or `ping` ok, or `serve` stopped cleanly |
| 1 | `failed` |
| 2 | Usage or configuration error. No request is sent. |
| 3 | `timed_out`, confirmed by the Claude side |
| 4 | `communication_error` (outcome unknown) |
| 5 | `rejected` |
| 6 | `running`: not finished, or the wait budget ran out |

Usage notes for whoever drives the ChatGPT side, which is you during testing or an agent later. They will be published in `docs/bridges.md`. In outline:

```
Delegate a task to Claude:   orbital-bridge submit --prompt-file task.md
The command prints one JSON object; read "status" first.
- succeeded: Claude Code reported that it finished. "response" is its final message.
  Read it to judge whether the task was really accomplished; the bridge does not check.
- failed / timed_out / rejected: read error.code and error.message.
- communication_error: the outcome is unknown. The task may still be running.
- running: not finished yet (or this command stopped waiting).
  Continue with:  orbital-bridge wait <task_id> --max-wait 600
```

### Risks

| # | Risk | Mitigation |

| R1 | The proxy strips or rewrites the `X-Orbital-*` headers | D-2 detects it in your dual-sandbox run. The fallback is to carry the same fields in an `Authorization: ORBITAL-HMAC-SHA256 …` header, as a `change:`. |

| R7 | A server restart loses records and the per-lifetime guarantees | Documented in §10. It surfaces as `unknown_task`, never as success. |

| R9 | A server crash leaves an orphaned Claude Code process | Documented in §10 and §14. Hardening is deferred. |
| R10 | Tool processes survive termination of the Claude Code process | F-4: they run in their own sessions, outside the process group. Claude cleans them up on SIGTERM; descendant-tree termination covers the SIGKILL path (§10). |
| R11 | Plain HTTP gives no confidentiality | Documented in §9. TLS is deferred. |
| R12 | Only Python 3.13 is available here, but the target is 3.11 or later | 3.11 compatibility is enforced statically through the mypy and ruff target version. Your sandboxes run whichever Python they have, 3.11 or later. |
| R13 | `http.server` is not hardened for production use | Authentication comes first, with size limits and socket timeouts, in a single-host deployment. |
