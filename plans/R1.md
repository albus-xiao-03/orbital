## 1. Summary

`orbital` will be a Python package that uses only the standard library. Its subpackage `orbital.bridges` lets a ChatGPT agent in one Docker Sandbox hand a prompt to Claude Code in a second Docker Sandbox and get Claude's answer back. The two sides talk only over the network.

- **Claude side.** `orbital-bridge serve` runs a small HTTP server. It authenticates every request, passes the prompt to `claude -p`, and keeps the result under the task id. Claude does the work; the bridge only carries the prompt and the result.
- **ChatGPT side.** `orbital-bridge submit …` (or the `BridgeClient` Python API) creates the task id, sends the prompt, polls until the task ends, and prints one structured JSON result.
- **Results.** Every result carries the task id and exactly one status. The terminal statuses are `succeeded`, `failed`, `timed_out`, `communication_error` and `rejected`; `running` is reported while the task is in progress. A result also carries either Claude's response or an error code with a message.
- **Trust.** Requests and responses are both signed with HMAC-SHA256 under a pre-shared key. A response that is unsigned, or whose signature does not verify, can only produce a failure status. It can never produce `succeeded`.

### Interpretations — please confirm or correct (Q2 in §17)

- **I1. Commit granularity.** I read `initial`, `change` and `remove` as file-level operations. Each commit therefore contains exactly one file and one operation on it:
  - creating it (subject prefix `add:`, which matches this repository's history);
  - modifying it (prefix `change:`);
  - deleting it (prefix `remove:`).

  Line-level edits are not split further: all edits made to one file for one purpose go into that file's single `change:` commit. Code files and documentation files never share a commit. Every commit has a subject, a descriptive body and the `Co-Authored-By` trailer.

- **I2. "Static helper objects".**
  - An *implementation component* is a type, together with its methods: a class, dataclass, enum, `Protocol`, or a subpackage's exception family. An entry-point callable such as `main()` also counts.
  - A *static helper object* is anything that supports a component without being one: a module-level function, a module-level constant or table, or a `@staticmethod` used as a utility.
  - Logic used inside only one method stays inline in that method.
  - Anything factored out to be shared is a helper, and it moves to a `utils` module (rule M2 in §6).

- **I3. Temporary files.** These are the files I create to get the work done. Program-generated files such as `__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`, `*.egg-info` and `build/` are outside the definition and are already git-ignored. Where it is easy, their caches are still pointed into `.tmp/r1/`.

- **I4. Tests.** The temporary harness may be as thorough as needed to guarantee quality. It is never committed and never deleted.

## 5. Architecture and key decisions

### Topology

```
ChatGPT sandbox
  ChatGPT agent (e.g. Codex CLI)
    └─ orbital-bridge submit …  ............................. BridgeClient
         │  HTTP/1.1 + JSON, HMAC-signed in both directions
         │  leaves through the sandbox egress proxy (which applies network policy)
         ▼
Docker host   http://host.docker.internal:8765  →  published port  →  Claude sandbox :8765
              (the user sets up port publishing and policy; orbital never touches Docker)
         │
         ▼
Claude sandbox
  orbital-bridge serve  ..................................... BridgeServer (binds 0.0.0.0:8765)
    ├─ authenticate each request, sign each response
    ├─ TaskRegistry: at most one running task; results kept by task id
    └─ TaskRunner → ClaudeCodeExecutor
         └─ claude -p --output-format json --session-id <task_id>   (prompt on stdin)
              Claude performs the task; the bridge only carries prompt and result
```

### Happy-path sequence

```
ChatGPT agent    BridgeClient                          BridgeServer                Claude Code
     │ run(prompt)   │                                       │                          │
     │──────────────▶│ task_id = uuid4()                     │                          │
     │               │ POST /v1/tasks (signed) ─────────────▶│ authenticate, admit      │
     │               │◀────────── 202 running (signed) ──────│ start runner ───────────▶│ claude -p  (stdin)
     │               │ GET /v1/tasks/{id}, every 2 s ───────▶│                          │ …works…
     │               │◀────────── 200 running ───────────────│                          │
     │               │                                       │◀──── JSON result ────────│
     │               │ GET /v1/tasks/{id} ──────────────────▶│ record → succeeded       │
     │               │◀────── 200 succeeded + response ──────│                          │
     │◀─ TaskResult ─│ verify signature and task_id          │                          │
```

### Decisions

| # | Decision | Rationale | Rejected alternatives |
|---|---|---|---|
| D1 | **Roles.** The Claude side is the HTTP server and the ChatGPT side is the client. One port is published from the Claude sandbox. | This matches the direction of delegation and needs only one inbound port. Outbound HTTP through the proxy is the supported way out of a sandbox. | A ChatGPT-side server polled by Claude: it just moves the port, with no gain. A third relay process: an extra component, outside the scope. |
| D2 | **Transport.** HTTP/1.1 and JSON on the standard library (`http.server.ThreadingHTTPServer`, `urllib.request`). | The sandbox egress is an HTTP forward proxy. Nothing has to be installed in either sandbox. | Raw TCP framing: may not pass the proxy. WebSockets or gRPC: need dependencies and are uncertain through the proxy. |
| D3 | **Asynchronous tasks.** `POST` returns `202` straight away and the client polls with `GET`. | Claude tasks can run for minutes or hours. A dropped connection loses nothing, and results can still be fetched by id after a client restart. | One long blocking request: dies at proxy idle timeouts and loses the result on disconnect. |
| D4 | **Task identity.** The client generates a UUID4 before any I/O. The server enforces uniqueness for its whole lifetime and treats an identical resubmission as idempotent. | Every outcome carries the id, including a submission that failed (O8). Retries are safe. A task id is never run twice. | Server-assigned ids: a failed submission would have no id. |
| D5 | **Capacity.** At most one task runs at a time; any other submission gets `rejected` / `server_busy`. | Concurrency and workload management are out of scope. The HTTP server is threaded only so that polls are answered while a task runs. | A FIFO queue: that is workload management, with extra state. |
| D6 | **Authentication.** HMAC-SHA256 with a pre-shared 256-bit key. Requests are signed with a timestamp and nonce and checked against a replay cache. Responses are signed and bound to the request nonce. | Works over plain HTTP through the proxy. The key is never transmitted. It is mutual: the client can prove a success really came from the bridge server. | A bearer token: replayable, and responses are not authenticated. mTLS: certificate handling, and a risk of proxy interception. |
| D7 | **Delegation.** Run `claude -p --output-format json --session-id <task_id>` with the prompt on stdin, in its own process group, with the deadline enforced. | Claude does the work (O12). Stdin avoids the Linux limit of 128 KiB per argument and keeps the prompt out of `ps`. The JSON output carries explicit error flags. Using the task id as the session id makes runs traceable. | The Agent SDK: a third-party dependency. `--output-format text`: gives no error signal. |
| D8 | **Reporting.** The client API returns a `TaskResult` for every outcome and raises exceptions only for programmer errors. | Nothing is silently discarded (AC4). | Exceptions for network errors: too easy to lose. |
| D9 | **Statuses.** `running` plus five terminal statuses, one of which is `rejected`. | Refused requests are not execution failures, communication failures or timeouts. A separate status keeps the four required distinctions clean. | Folding authentication failures into `communication_error`. |
| D10 | **State.** An in-memory registry that keeps the last 100 finished results. | R1 is about communication. A lost record is reported as `communication_error` / `unknown_task`, never as success. | A persistent store: outside the R1 scope. |
| D11 | **Footprint.** Standard library only, Python 3.11 or later. | Portable to the other sandbox, and `.env` needs no new packages. | requests, aiohttp or FastAPI: would need installing on both sides. |
| D12 | **ChatGPT interface.** The `orbital-bridge` CLI (JSON on stdout, exit code reflects the status) plus the Python API. | A sandboxed ChatGPT agent such as Codex CLI runs shell commands, and JSON is unambiguous. | An MCP tool server: deferred (§18). |

### Module rules

- **M1 — One component per file.** Each implementation file holds one public component and its methods. The only exception is `errors.py`, which holds the exception family of its subpackage.
- **M2 — Helper placement (interpretation I2).**
  - A subpackage keeps its static helpers out of its implementation files.
  - If the helpers form one cohesive group, they go in `<subpackage>/utils.py`.
  - If they belong to different implementation files, they go in a `<subpackage>/utils/` subpackage. That subpackage has one module per owning implementation file, with the same base name, plus `common.py` for helpers shared by several files.
  - The helper inventory in the tree above is what I expect; implementation may refine it within this rule.
- **M3 — No import cycles.**
  - Subpackage `__init__.py` files contain only a docstring.
  - The public API is re-exported only from `orbital/bridges/__init__.py`.
  - Internal imports always name leaf modules, for example `from orbital.bridges.models.task_status import TaskStatus`.
  - `utils` modules never import their own package's `__init__`.
- **M4 — Layering.** `models` and `auth` depend on nothing else in `orbital`. The other subpackages depend on each other as follows:

  | Subpackage | Depends on |
  |---|---|
  | `protocol` | `models` |
  | `config` | `auth` |
  | `executors` | `models` |
  | `server` | `models`, `auth`, `protocol`, `config`, `executors` |
  | `client` | `models`, `auth`, `protocol`, `config` |
  | `cli` | all of the above |

  `server` and `client` never import each other.
- **M5 — Style.** Full type hints, clean under `mypy --strict` (target Python 3.11) and `ruff check` / `ruff format`. Public components get docstrings. Any `noqa` must state its reason; for example, binding `0.0.0.0` is intentional (S104) and the single Claude subprocess call is intentional (S603).

## 7. Domain model

### `TaskStatus`

| Value | Terminal | Meaning |
|---|---|---|
| `running` | no | Accepted; Claude is working on the task |
| `succeeded` | yes | Claude completed the task; `response` holds its final result text |
| `failed` | yes | The task reached the Claude side, but execution failed |
| `timed_out` | yes | Execution went past its deadline |
| `communication_error` | yes | The exchange with the server failed; the task's state is unknown |
| `rejected` | yes | The server refused the request; the task was not executed |

### `ErrorCode`

Each code belongs to exactly one category, given by `ErrorCode.category`. A `TaskResult` whose error code does not match its status is invalid.

| Code | Category | Produced by | Meaning |
|---|---|---|---|
| `unauthorized` | `rejected` | server (401) | Authentication failed; the reason is in the message |
| `invalid_request` | `rejected` | server (400/404/405/411) | The request was malformed, invalid, or for an unknown route |
| `payload_too_large` | `rejected` | server (413) or client pre-check | The request body is over the size limit |
| `server_busy` | `rejected` | server (409) | Another task is running; the message names it |
| `task_id_conflict` | `rejected` | server (409) | The task id was already used for different content, or its record has been evicted |
| `connection_failed` | `communication_error` | client | Could not connect (refused, DNS failure, unreachable) |
| `connection_interrupted` | `communication_error` | client | The connection dropped mid-exchange |
| `request_timeout` | `communication_error` | client | No response within the per-request timeout |
| `gateway_error` | `communication_error` | client | The proxy or gateway answered 502, 503 or 504 |
| `network_policy_blocked` | `communication_error` | client | The sandbox proxy refused the request (403); its message is included |
| `response_unverified` | `communication_error` | client | The response signature is missing or invalid |
| `invalid_response` | `communication_error` | client | The response is malformed or inconsistent, or has an unexpected status |
| `unknown_task` | `communication_error` | server (404) | The server has no record of the task (restart, retention limit, or wrong server) |
| `server_error` | `communication_error` | server (500) | An unexpected bridge-server error |
| `claude_error` | `failed` | executor | Claude Code reported an error result |
| `executor_failed` | `failed` | executor | Claude Code exited abnormally without a valid success result |
| `executor_unavailable` | `failed` | executor | Claude Code could not be started |
| `invalid_executor_output` | `failed` | executor | Claude Code's output could not be interpreted |
| `execution_cancelled` | `failed` | executor | Execution stopped because the server shut down |
| `internal_error` | `failed` | server task runner | An unexpected bridge error while running the task |
| `execution_timeout` | `timed_out` | executor | The deadline was reached and the Claude Code process group was terminated |
| `deadline_exceeded` | `timed_out` | client | The task was still reported `running` after its deadline plus a grace period |

### `ErrorDetail`, `TaskRequest`, `TaskResult`, `HealthReport`

All four are frozen dataclasses. They are validated in `__post_init__` and invalid values raise `ValueError`.

- **`ErrorDetail(code: ErrorCode, message: str)`.** The message is non-empty and capped at 4,000 characters; longer messages are truncated with a marker.
- **`TaskRequest(task_id, prompt, timeout_seconds)`.**
  - `task_id` is a canonical, lowercase UUID version 4.
  - `prompt` is a `str` that is not blank.
  - `timeout_seconds` is an `int` of at least 1; a `bool` is not accepted. The server also enforces its own maximum.
- **`TaskResult(task_id, status, response, error)`** has these invariants:
  - `running` → `response is None` and `error is None`.
  - `succeeded` → `response` is a `str` (it may be empty) and `error is None`.
  - Any other status → `response is None`, `error` is present, and `error.code.category` equals `status`.
- **`HealthReport(ok, busy, error)`.** If `ok` is true, `error is None` and `busy` is a `bool`. If `ok` is false, `error` is present.

The JSON form, shared by the wire protocol and the CLI:

```json
{"task_id": "0b6c1c2e-6f5d-4c9a-9a51-3f2f6d0c8e11", "status": "succeeded", "response": "…Claude's final answer…", "error": null}
{"task_id": "0b6c1c2e-6f5d-4c9a-9a51-3f2f6d0c8e11", "status": "timed_out", "response": null,
 "error": {"code": "execution_timeout", "message": "Claude Code did not finish within 1800 s; its process group was terminated"}}
```

## 8. Wire protocol v1

### Endpoints

| Method and path | Purpose | Success | Errors |
|---|---|---|---|
| `POST /v1/tasks` | Submit a task | `202` for a new task; `200` for an identical resubmission (returns the current record) | 400, 401, 409, 411, 413 |
| `GET /v1/tasks/{task_id}` | Current record of a task (`running` or terminal) | `200` | 401, 404 |
| `GET /v1/health` | Authenticated liveness check, plus the `busy` flag | `200` | 401 |

### Bodies

All bodies are UTF-8, compact JSON objects.

- **Submit request.** Exactly these keys: `{"task_id": "<uuid4>", "prompt": "<text>", "timeout_seconds": 1800}`.
- **Task record** (`200`/`202`). The `TaskResult` JSON shown in §7. The server only ever reports `running`, `succeeded`, `failed` or `timed_out`.
- **Error** (`4xx`/`5xx`). `{"error": {"code": "<ErrorCode>", "message": "<text>"}, "task_id": "<uuid>" or null}`.
- **Health.** `{"service": "orbital-bridge", "protocol_version": "1", "busy": false}`.

Decoding is strict on both sides. A message is rejected if it:

- is not a JSON object at the top level;
- has duplicate keys, `NaN` or `Infinity`;
- has unknown or missing keys;
- has a value of the wrong type (`true` is not an integer).

### Headers

| Header | Direction | Value |
|---|---|---|
| `X-Orbital-Protocol` | both | `1` |
| `X-Orbital-Timestamp` | request | Unix time in whole seconds |
| `X-Orbital-Nonce` | request | 16 random bytes as 32 lowercase hex characters |
| `X-Orbital-Signature` | request; response (authenticated requests only) | HMAC-SHA256 as 64 lowercase hex characters |
| `Content-Type` / `Content-Length` | both | `application/json; charset=utf-8` and the exact byte length. Chunked bodies are not supported. |
| `WWW-Authenticate` | `401` response | `ORBITAL-HMAC-SHA256` |

Every response also carries `Connection: close` and `Cache-Control: no-store`.

### Signatures

The canonical strings are joined with `\n`, with no trailing newline. The signature is `hex(HMAC-SHA256(key, utf8(canonical)))`.

```
request:                  response:
ORBITAL-HMAC-SHA256       ORBITAL-HMAC-SHA256
1                         1
request                   response
<METHOD>                  <METHOD of the request>
<TARGET>                  <TARGET of the request>
<TIMESTAMP>               <NONCE of the request>
<NONCE>                   <HTTP status code>
<SHA256-hex of body>      <SHA256-hex of body>
```

- The `request` and `response` labels separate the two kinds of signature, so neither can be replayed as the other.
- `TARGET` is the origin-form path, for example `/v1/tasks/<id>`. The server normalises absolute-form targets sent through a proxy (`http://host:port/v1/…`) by dropping the scheme and authority. The client signs only the path of the URL, and no endpoint uses a query string.
- An empty body hashes as SHA-256 of the empty string.

### HTTP statuses used by the server

| Status | When | Signed? |
|---|---|---|
| `200` | A task record (`GET`, idempotent `POST`) or the health check | yes |
| `202` | A new task was accepted | yes |
| `400` | Invalid JSON, fields or values (`invalid_request`) | yes |
| `401` | Authentication failed (`unauthorized` plus a reason) | **no** — the peer is not authenticated |
| `404` | Unknown task (`unknown_task`) or unknown route (`invalid_request`) | yes |
| `405` | Method not allowed (`invalid_request`) | yes |
| `409` | `server_busy` or `task_id_conflict` | yes |
| `411` | Missing `Content-Length` on `POST`, a chunked body, or a body on `GET` (`invalid_request`) | no — checked before the body is read |
| `413` | `Content-Length` over the limit (`payload_too_large`) | no — checked before the body is read |
| `500` | Unexpected server error (`server_error`) | yes |

The limits are a request body of at most 1 MiB, `timeout_seconds` between 1 and 14,400, and a socket read timeout of 30 s per connection.

## 9. Authentication and security model

### Key

- `orbital-bridge keygen` prints 32 random bytes from `secrets`, encoded as base64url without padding (43 characters).
- `SharedKey` accepts only text that decodes to at least 32 bytes.
- The key reaches each sandbox only through the environment variable `ORBITAL_BRIDGE_KEY`. There is no CLI flag for it, so it never appears in shell history or `ps`, and it is never put in a shared file.
- `repr()` of a `SharedKey` is redacted, and the key is never logged.

### Server-side request verification (`MessageVerifier`)

The server runs these checks in order and returns `401` with a coarse reason on the first failure. The reason is never secret.

1. All credential headers are present and well-formed. Reasons: `missing_credentials`, `malformed_credentials`.
2. `X-Orbital-Protocol` is `1`. Reason: `unsupported_protocol`.
3. The timestamp is within ±300 s of the server clock. Reason: `timestamp_out_of_window`.
4. The signature matches, compared in constant time with `hmac.compare_digest`. Reason: `invalid_signature`.
5. The nonce has not been seen within the last 600 s. Nonces are recorded only after the signature has verified, so unauthenticated traffic cannot fill the cache. Reason: `replayed_nonce`.
6. The cache is bounded at 100,000 entries. If it is still full after expired entries are purged, the request is refused rather than weakening replay protection. Reason: `nonce_cache_full`.

Authentication happens before routing and before any JSON parsing. An unauthenticated request never reaches the task service or the executor.

### Client-side response verification

- A `2xx` response counts only if its `X-Orbital-Signature` verifies against the request's method, target and nonce, its status code, and its body.
- The only responses the server legitimately leaves unsigned are `401`, `411` and `413`. They map to `rejected`.
- Every other unsigned or wrongly signed response maps to `communication_error`: either `response_unverified`, or a proxy outcome such as `network_policy_blocked` or `gateway_error` (§11).
- As a result, a proxy page, a man-in-the-middle, or the wrong service at the URL can never produce `succeeded`.

### Hygiene

- All `ORBITAL_BRIDGE_*` variables are removed from the Claude Code child environment.
- Logs contain task ids, sizes, statuses, durations, peers and failure reasons. They never contain prompts, responses or the key.
- The server advertises a generic `Server` banner.
- There is no switch that disables authentication, and the server refuses to start without a valid key.

### Threat model and limitations

**Protected against:**

- Task submission or result reading by anyone who can reach the port without the key.
- Tampering with a request or response.
- Replaying captured requests.
- A forged or proxy-injected response being accepted as success.

**Not protected against:**

- **Confidentiality.** Plain HTTP means prompts and responses can be read on the host's network path. That is acceptable when both sandboxes are on one host; TLS is deferred (§18).
- **The key holder.** Anyone with the key has full delegation power, so the key is as sensitive as shell access in the Claude sandbox.
- **Floods of unauthenticated requests.** Socket timeouts limit them, but they are not fully mitigated.

The Claude side runs each prompt with whatever permissions its Claude Code is configured to have; Docker Sandboxes default to `bypassPermissions`. The sandbox is the isolation boundary.

## 10. Claude-side server and executor

### Request pipeline (`BridgeRequestHandler`)

1. **Normalise the target.** An absolute-form target from a proxy becomes origin-form.
2. **Check framing.**
   - A `GET` must have no body.
   - A `POST` needs `Content-Length`; a chunked body or a missing length gets `411`.
   - A body over the limit gets `413`, and the body is not read.
3. **Read** exactly `Content-Length` bytes, with a socket timeout of 30 s.
4. **Authenticate** (§9). On failure, return an unsigned `401`.
5. **Route.** An unknown path gets `404` and a wrong method gets `405`.
6. **Decode strictly.** On failure, return `400`.
7. **Call `TaskService`.** It returns `202`, `200`, `404` or `409`.
8. **Sign the response,** binding it to the request nonce, and send it with `Connection: close`.

An unexpected exception anywhere in steps 5–8 returns a signed `500 server_error` and is logged with a stack trace. HTTP logging goes through `logging`, not stderr prints.

### Components

- **`TaskRegistry`** is a thread-safe store. `admit(request)` applies these rules in order:
  1. If the id is known and its record is retained with the same fingerprint (SHA-256 over the prompt and timeout), return the existing record (`200`). This is the idempotent replay.
  2. If the id is known but the content differs, or its record has been evicted, raise `TaskConflictError` (`409 task_id_conflict`).
  3. If another task is running, raise `ServerBusyError` (`409 server_busy`, naming the running id).
  4. Otherwise create a `running` record (`202`).

  Ids are remembered for the lifetime of the process. The server keeps at most 100 finished records and evicts the oldest; it never evicts the running one.
- **`TaskRunner`** starts one worker thread per accepted task, and the registry guarantees at most one is alive. The worker calls `executor.execute(request)` and converts the `ExecutionOutcome` into a `TaskResult` with the same task id. Any exception becomes `failed` / `internal_error`. The runner logs completion with its duration.
- **`TaskService`** is the facade used by the handler: `submit`, `status`, `health` and `shutdown`.
- **`BridgeServer`** is built from a `ServerConfig` and an `Executor`. It binds on construction, so `server_address` is known even when the port is 0. It provides `serve_forever()`, a thread-safe `shutdown()` (stop accepting, cancel the running task, join the runner for at most 10 s, close the socket) and context-manager support.

### Executor (`ClaudeCodeExecutor` on top of `ProcessRunner`)

- **Command:**
  ```
  [claude_bin, *claude_args, "-p", "--output-format", "json", "--session-id", task_id]
  ```
  The fixed flags come last so that they win over anything in `claude_args`. `claude_args` defaults to `--permission-prompts none`, so a tool call that would prompt for permission is denied instead of blocking. The configured permission mode still applies.
- **Input:** the prompt's UTF-8 bytes, written to stdin by a separate writer thread that then closes stdin. Doing this in a separate thread avoids a pipe deadlock with large prompts.
- **Process setup:**
  - working directory `workdir`;
  - environment: the server's own, minus every `ORBITAL_BRIDGE_*` variable;
  - `start_new_session=True`, so the whole process tree can be signalled.
- **Output capture:**
  - stdout is captured up to 32 MiB; beyond that it is flagged as truncated and drained;
  - stderr keeps its last 64 KiB.
- **Deadline or cancellation:**
  1. Send `SIGTERM` to the process group.
  2. Wait a 5 s grace period, then send `SIGKILL`.
  3. After the main process exits, give the readers 5 s to finish. If a descendant is still holding a pipe open, kill the group.
- **Platform:** POSIX only, which is what the Linux sandboxes provide.

**Outcome mapping.** The JSON content is the source of truth and the exit code is a second, required condition. Success therefore needs both.

| Observation | Outcome |
|---|---|
| The executable is missing or not executable | `failed` / `executor_unavailable` |
| The deadline was reached | `timed_out` / `execution_timeout` |
| Cancelled by server shutdown | `failed` / `execution_cancelled` |
| Exit code 0, and the result object has `is_error: false`, `subtype: "success"` and a string `result` | `succeeded`, with `response` set to `result` verbatim |
| The result object has `is_error: true` or a non-success `subtype` | `failed` / `claude_error`. The message includes the subtype and excerpts of `result` and/or `errors`. |
| The result object says success but the exit code is not 0 | `failed` / `executor_failed`. The contradiction is reported; it is never treated as success. |
| No parsable result object, and the exit code is not 0 | `failed` / `executor_failed`, with the exit code or signal and the stderr tail |
| No parsable result object, and the exit code is 0; or stdout was truncated | `failed` / `invalid_executor_output` |

- The "result object" is the stdout JSON object with `type: "result"`. If stdout is a JSON array, which may happen if `--verbose` was added to `claude_args`, it is the last element with `type: "result"`.
- Fields such as `usage`, `total_cost_usd`, `duration_*` and `num_turns` are deliberately ignored, because token and cost accounting is out of scope.

### Shutdown and logging

- **Shutdown.** `SIGINT` or `SIGTERM` stops the accept loop (via `shutdown()` called from a helper thread), cancels the running Claude process group, joins the runner and exits with status 0. Records are in memory and are lost on exit, as documented.
- **Logging** goes to stderr:
  - `INFO`: startup (address, workdir, Claude binary; never the key), each task accepted (id, prompt size, timeout) and each task finished (id, status, code, duration);
  - `WARNING`: authentication failures (reason and peer);
  - `DEBUG`: polls.

## 11. ChatGPT-side client

### API

These methods never raise for task or communication outcomes. They raise `ValueError` or `TypeError` only for invalid arguments.

```python
client = BridgeClient(ClientConfig.from_env())
client.submit(prompt, *, timeout_seconds=None, task_id=None) -> TaskResult  # running, or an early terminal/failed result
client.status(task_id) -> TaskResult                                       # a single poll
client.wait(task_id, *, max_wait_seconds) -> TaskResult                    # terminal, or the last `running` snapshot
client.run(prompt, *, timeout_seconds=None) -> TaskResult                  # submit + wait; always terminal
client.ping() -> HealthReport
```

### Algorithms

- **`submit`**
  1. Validate the arguments.
  2. Take the task id from `task_id` or generate a UUID4.
  3. Encode the body. If it exceeds `max_request_bytes`, return `rejected` / `payload_too_large` without sending anything.
  4. Send the `POST`. On retryable failures, retry it with the same body and a fresh nonce; this is safe because submission is idempotent.
  5. Map the reply to a `TaskResult`.
- **`wait`** polls every `poll_interval` (2 s) until the status is terminal. When `max_wait_seconds` runs out it returns the latest `running` snapshot; that is not a timeout, because the task's own deadline is enforced by the server.
- **`run`** calls `submit`, then polls until a terminal status or until the deadline: submission time + `timeout_seconds` + a 30 s grace period. If the task is still `running` at the deadline, `run` returns `timed_out` / `deadline_exceeded`. The grace period lets the server report its own `execution_timeout` first.
- **Retries.**
  - The retryable codes are `connection_failed`, `connection_interrupted`, `request_timeout` and `gateway_error`.
  - Backoff is 1, 2, 4, 8, then 16 s, capped at 30 s.
  - At most 5 consecutive failures are allowed, and the counter resets after any successful exchange.
  - When the retry budget runs out after the task was accepted, the `communication_error` message says the task may still be running and can be retrieved later with `orbital-bridge wait <task_id>`.

### Mapping replies to results (`client/utils/bridge_client.py`, `client/utils/http_transport.py`)

| Observation | Status | Code | Retried |
|---|---|---|---|
| Connection refused, DNS failure, unreachable | `communication_error` | `connection_failed` | yes |
| Connection reset, remote disconnected, incomplete read | `communication_error` | `connection_interrupted` | yes |
| Socket timeout | `communication_error` | `request_timeout` | yes |
| Unsigned `502`, `503` or `504` (proxy or gateway) | `communication_error` | `gateway_error` | yes |
| Unsigned `403` (sandbox network policy) | `communication_error` | `network_policy_blocked` | no |
| Unsigned `401` | `rejected` | `unauthorized` (plus the server's reason, if any) | no |
| Unsigned `411` / `413` | `rejected` | `invalid_request` / `payload_too_large` | no |
| Any other unsigned response, or a bad signature | `communication_error` | `response_unverified` | no |
| Verified `200`/`202` with a valid record for this task id | the record's status | the record's error code | — |
| Verified `2xx` that cannot be decoded, has the wrong task id, or has a status the server never reports | `communication_error` | `invalid_response` | no |
| Verified `4xx`/`5xx` with a valid error body | the body code's category | `invalid_request`, `payload_too_large`, `server_busy`, `task_id_conflict`, `unknown_task` or `server_error` | no |
| Verified `4xx`/`5xx` with an unknown or inconsistent code | `communication_error` | `invalid_response` | no |

### Proxy handling

- By default `urllib` honours `HTTP_PROXY` and `NO_PROXY`, which is required inside sandboxes. `--no-proxy` (`use_env_proxy=False`) turns this off for direct loopback use.
- The messages for `network_policy_blocked` and `gateway_error` include up to 500 characters of the proxy's body, for example `Approval required for host.docker.internal`, so the operator can see what to fix.
- `ClientConfig` accepts only `http://host[:port]` URLs, with no path, query or userinfo.

## 12. Command-line interface

The console script is `orbital-bridge`, which is the same as `python -m orbital.bridges`. Results are printed to stdout as a single JSON object; logs and diagnostics go to stderr.

| Command | Side | Purpose | Main options |
|---|---|---|---|
| `serve` | Claude | Run the bridge server (checks first that the Claude binary and the workdir exist) | `--host`, `--port`, `--workdir`, `--claude-bin`, `--claude-arg` (repeatable), `--max-timeout`, `--log-level` |
| `submit` | ChatGPT | Submit a prompt; by default, wait for the terminal result | the prompt as `PROMPT`, `--prompt-file PATH` or `-` (stdin); `--timeout`; `--task-id`; `--detach`; `--url`; `--no-proxy` |
| `status` | ChatGPT | Print the current record of a task | `TASK_ID`, `--url`, `--no-proxy` |
| `wait` | ChatGPT | Poll until the task is terminal or `--max-wait` runs out | `TASK_ID`, `--max-wait` (default: client timeout + grace), `--url`, `--no-proxy` |
| `ping` | ChatGPT | Authenticated round trip; reports `ok` and `busy` | `--url`, `--no-proxy` |
| `keygen` | either | Print a new random shared key | — |

The exit code is determined only by the status that was printed:

| Exit code | Meaning |
|---|---|
| 0 | `succeeded`; or `ping` ok, `keygen` done, `serve` stopped cleanly |
| 1 | `failed` |
| 2 | Usage or configuration error (for example a missing key or a bad URL). No request is sent. |
| 3 | `timed_out` |
| 4 | `communication_error` |
| 5 | `rejected` |
| 6 | `running` (`submit --detach`, `status`, or `wait` whose budget ran out) |

The usage notes for the ChatGPT-side agent will be published in `docs/bridges.md`, ready to paste into that agent's instructions (for example an `AGENTS.md`). In outline:

```
Delegate a task to Claude:  orbital-bridge submit --prompt-file task.md
The command prints one JSON object. Use "response" only when "status" is "succeeded";
otherwise read error.code / error.message (failed, timed_out, communication_error, rejected).
For long tasks: orbital-bridge submit --detach --prompt-file task.md
then repeat     orbital-bridge wait <task_id> --max-wait 600   until "status" is not "running".
```

## 14. Deployment across two Docker Sandboxes

These are operator steps. `orbital` itself performs none of the Docker or `sbx` actions (objective 5). The bridge only ever uses the configured URL, and any address that is reachable through the policy works, for example a LAN IP.

**Prerequisites**

- Both sandboxes have Python 3.11 or later and their own copy of this repository.
- In the Claude sandbox, Claude Code is authenticated and can run tools unattended. Docker Sandboxes do this by default with `bypassPermissions`.

**Steps**

1. **Key.** In either sandbox, run `orbital-bridge keygen` and keep the output safe.
2. **Claude sandbox.**
   - Install from its own checkout with `python -m pip install .`. Without installing, `PYTHONPATH=src python -m orbital.bridges …` also works.
   - `export ORBITAL_BRIDGE_KEY=<key>`.
   - Start the server with `orbital-bridge serve --port 8765 --workdir <project dir>`.
3. **Host (you).** Publish the port: `sbx ports <claude-sandbox> --publish 127.0.0.1:8765:8765`.
4. **Host (you).** Let the ChatGPT sandbox reach it: `sbx policy allow network localhost:8765`, and approve any pending approval. The exact syntax and options of `sbx policy` should be checked with `sbx policy --help`.
5. **ChatGPT sandbox.**
   - Install as in step 2.
   - `export ORBITAL_BRIDGE_KEY=<key>` and `export ORBITAL_BRIDGE_URL=http://host.docker.internal:8765`.
   - Run `orbital-bridge ping`; the expected output is `{"ok": true, "busy": false, "error": null}`.
   - Then `orbital-bridge submit --prompt-file task.md`.
6. **ChatGPT agent.** Give it the usage snippet from §12.

Each sandbox gets the key through its own environment. A key file on a mount shared by both sandboxes is explicitly discouraged, because objective 6 rules out shared filesystems.

## 17. Risks, assumptions and open questions

### Risks

| # | Risk | Mitigation |
|---|---|---|
| R1 | The proxy strips or rewrites the custom `X-Orbital-*` headers, or limits bodies | Stage B detects it with `ping`. The fallback is to carry the same fields in one standard `Authorization: ORBITAL-HMAC-SHA256 …` header. |
| R2 | The two sandbox clocks differ by more than 300 s | Requests fail with `401 timestamp_out_of_window`, which `ping` reveals. The window is configurable. |
| R3 | Claude Code's output contract is not authoritatively documented: the docs were unreachable, the exit code is reportedly unreliable, and there is a report of `-p` exiting 0 before the task finished | Success requires exit code 0 **and** an explicit success JSON, and everything else is a failure. Stage A pins down the real behaviour. The bridge cannot detect the upstream "early exit 0" problem; this is documented. |
| R4 | Delivering the prompt on stdin is unconfirmed | Stage A checks it. The fallback is to pass the prompt as a positional argument after `--`, limited to the 128 KiB Linux per-argument limit, with `payload_too_large` above that. |
| R5 | A permission prompt blocks an unattended run | The default `--permission-prompts none`, plus the Docker Sandboxes default `bypassPermissions`. In the worst case the task ends at its deadline as `timed_out`; it never hangs forever. |
| R6 | The ChatGPT agent's shell commands have a time limit | `submit --detach` followed by repeated `wait --max-wait …`. |
| R7 | A server restart loses its in-memory records | Reported as `communication_error` / `unknown_task`, never as success. Documented. |
| R8 | Plain HTTP gives no confidentiality | Documented in §9. TLS is deferred. |
| R9 | Only Python 3.13 is available here, but the target is 3.11 or later | 3.11 compatibility is enforced statically through the mypy and ruff target version. It cannot be tested at runtime in this environment. |
| R10 | `http.server` is not hardened for production use | Authentication comes first, with size limits and socket timeouts, in a single-host deployment. Floods of unauthenticated requests are not fully mitigated (§9). |

### Assumptions

- **A1.** "ChatGPT" means a ChatGPT- or Codex-style agent running in its own Docker Sandbox, with shell access, so it can run the CLI.
- **A2.** Both sandboxes run on the same Docker host and reach each other through `host.docker.internal`. On different hosts, a reachable host address works the same way.
- **A3.** Each sandbox installs `orbital` from its own copy of the repository.
