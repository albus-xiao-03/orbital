### QA-01 — The documented server command loses every line logged during a Ctrl-C stop

| | |
|---|---|
| Severity | High: it blocks D-9 and, through it, AC4 and AC6 |
| Classification | A defect in the acceptance procedure and setup instructions. No defect was found in the `orbital.bridges` code for this observation. |
| Where | `plans/R1.md` §14 C (the server start, followed by "Stop it with Ctrl-C") and §16 D-8 and D-9 (the same command and stop). It was repeated word for word in the removed harness's checkpoint text (`R1Procedure.SERVE` at `3b776e3`). `README.md` and `docs/bridges.md` do not use `tee` and are not affected. |
| Status | Open |

**Observation.** After the D-9 stop, `serve.log` held only `task 72fca0ac-25b7-485c-bc4f-f441c09e3deb accepted (prompt 65 bytes, execution timeout 1800 s)` for the task. The plan's expected result is that `serve.log` shows the task cancelled.

**What the server logs when it stops a running task.** The lines come from `cli/serve_command.py`, `executor/claude_code_executor.py` and `server/task_supervisor.py`. This is Stage R's `serve.log` at its D-9 stop (2026-11-11, local time):

```
20:54:06,460 INFO orbital.bridges.cli: stopping; the running task, if any, is terminated and reaped
20:54:07,044 INFO orbital.bridges.executor: task a77de183-…: Claude Code exited with status 143 after 5.7 s; 0 permission denial(s) reported
20:54:07,044 INFO orbital.bridges.server: task a77de183-… finished: failed (execution_cancelled) after 5.7 s
20:54:07,044 INFO orbital.bridges.cli: stopped
```

All four lines are written to stderr after the stop signal arrives.

**Mechanism.**

1. The documented command makes the server and `tee` one foreground job, so Ctrl-C makes the terminal send SIGINT to both.
2. `tee` (GNU coreutils, without `-i`) exits on SIGINT at once.
3. The server handles SIGINT as a graceful stop. By the time it logs the four lines, nothing is reading the pipe: the writes fail (`EPIPE`) and Python's logging handler swallows the error. The lines reach neither `serve.log` nor the terminal.
4. The stop itself completes: the task is terminated, reaped and recorded in memory. The server has no other log destination (plan §10: logging goes to stderr).

**Reproduction** (today, simulated Claude; details in Appendix B):

| Variant | Server command and stop | Task lines in `serve.log` | `stopping` / `stopped` logged | Left running 0.5–0.8 s after the stop |
|---|---|---|---|---|
| Documented (3 runs) | `serve … 2>&1 \| tee -a serve.log`, then Ctrl-C | `accepted` only | no | nothing |
| Control | `serve … 2>&1 \| tee -i -a serve.log`, then Ctrl-C | `accepted`; `exited with status 143`; `finished: failed (execution_cancelled)` | yes | nothing |
| Control | `serve … >> serve.log 2>&1`, then Ctrl-C | the same three lines | yes | nothing |

The documented variant reproduces your `serve.log` line for line. In the reproduction, the terminal also showed only `^C` and the next prompt; with `tee -i`, the four stop lines appear after `^C`.

**Impact.**

- With the documented setup, the Claude side never keeps a record of a stop: not the cancellation of a running task, not even `stopping` or `stopped`. D-9's expectation cannot be met as written, whatever the implementation does.
- Operators lose the only Claude-side record that tells a cancelled task from an orphaned one after a restart. On the client side, `unknown_task` is ambiguous by design (plan §10).

**What the returned evidence cannot settle.** The `serve.log` content is equally consistent with QA-02 (the terminal closed, with no graceful stop). Which one happened is recorded only in the Claude sandbox:

```bash
# Claude sandbox
grep -n -E 'orbital.bridges.cli: (listening|stopping|stopped)' ~/orbital-acceptance/serve.log
ls -l --time-style=full-iso ~/.claude/projects/*/72fca0ac-25b7-485c-bc4f-f441c09e3deb.jsonl
grep -c '"text":"SLEPT"' ~/.claude/projects/*/72fca0ac-25b7-485c-bc4f-f441c09e3deb.jsonl
```

- **The `listening` / `stopping` sequence.** The procedure also used Ctrl-C before and after D-8. If no `listening` line is ever followed by `stopping`, QA-01's mechanism is confirmed in your environment.
- **The task's Claude Code transcript.** It is named after the task id, which is also the session id, and it ends when the run ends.
  - Modified within seconds of the stop, with no `SLEPT` reply: the bridge terminated the run, and only QA-01 applies.
  - Ending a minute or more after 03:21:43Z with a `SLEPT` reply: the run outlived the server (QA-02).
  - This check works on Stage R's transcripts. The cancelled D-9 run (`a77de183-…`) has no `SLEPT` reply and was last written at the stop; the completed D-6 run (`354633a2-…`) has one.

### QA-02 — Closing the server's terminal (SIGHUP) is not a graceful stop

| | |
|---|---|
| Severity | Medium |
| Classification | An implementation gap: a new, undocumented trigger for the known orphan limitation (plan §10 "Crash or `SIGKILL`", risk R9) |
| Where | `cli/serve_command.py` makes only SIGINT and SIGTERM a graceful stop; SIGHUP keeps its default action, which ends the process. Plan §10, `README.md` and `docs/bridges.md` describe Ctrl-C, SIGTERM, a crash and SIGKILL, but not a hangup. |
| Status | Open. It is not known to have happened in your run (see QA-01). |

**Reproduction** (Appendix B, run `20261115T034829Z-hangup-3be2a9`). The documented pipeline was started, then the terminal was closed instead of typing Ctrl-C:

- The server was gone at once and logged nothing.
- 0.5 s later, the simulated Claude Code process and its `sleep 60` were still running, and both D-9 checks listed them.
- The script then stopped them.

**Impact.**

- A hangup happens whenever the terminal or session running the server goes away, for example when the window is closed or the connection to the sandbox drops.
- The Claude Code run keeps working on the prompt, with nothing to record its result.
- After a restart, the client gets `unknown_task`, and the operator has no Claude-side record of the run.
- Client-side behaviour stays correct, as in D-9b and D-9c.
